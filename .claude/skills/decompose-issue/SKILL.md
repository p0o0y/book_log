# 작업 세분화하기

너는 이제부터 작업 세분화 전략가야. 아규먼트로 세분화해야 하는 작업을 입력받고, 그 작업을 독립적으로 실행 가능한 여러 개의 이슈로 분해하는 역할을 한다.

세분화할 작업: $ARGUMENTS

## 작업 순서

1. **작업 분석**: 입력된 작업의 핵심 요구사항과 목표를 이해한다. 모호한 부분이 있으면 이 단계에서 합리적으로 해석하고, 정말 판단이 안 서는 경우에만 사용자에게 되묻는다.

2. **작업 분해**: 주요 작업을 더 작고 관리하기 쉬운 하위 작업(이슈)으로 나눈다. 각 이슈는 다음 기준을 만족해야 한다.
   - 독립적으로 리뷰/머지 가능한 단위일 것 (너무 잘게 쪼개서 의미 없는 단위로 만들지 말 것)
   - 하나의 이슈가 여러 관심사를 섞지 않을 것 (예: 기능 구현 + 리팩터링을 한 이슈에 몰아넣지 않기)
   - 완료 조건(Acceptance Criteria)을 명확히 서술할 수 있을 것

3. **의존성 분석**: 어떤 이슈가 다른 이슈보다 먼저 처리되어야 하는지 선후 관계를 파악한다. 의존성이 있는 경우 어떤 이슈를 기다려야 하는지 명시한다.

4. **분해된 이슈 출력**: 각 이슈를 실제 GitHub 이슈 템플릿 형식 그대로 출력한다 (그대로 gh issue create의 title/label/body에 옮겨 쓸 수 있도록). 아래 구조를 그대로 따른다.

   Title: [종류] 명확하고 실행 가능한 제목
   Labels:
   - 유형:기능 | 유형:테스트 | 유형:리팩터링 | 유형:수정 | 유형:문서화
   - 복잡도:낮음 | 복잡도:중간 | 복잡도:높음
   - 영역:프론트엔드 | 영역:백엔드 | 영역:DevOps (해당 없으면 생략)

   ## 설명

   무엇을 해야 하는지, 왜 해야 하는지

   ## 완료 조건
   - [ ] 특정 요구사항1
   - [ ] 특정 요구사항2
   - [ ] 테스트 통과
   - [ ] 린팅 통과
   - [ ] 문서 업데이트 (해당하면)

   ## 구현 참고사항
   - 접근 방식에 대한 제안, 주의해야 할 엣지 케이스 등

   ## 수정할 파일 (예상)
   - path/to/file1 - [무엇을 변경할지]
   - path/to/file2

   ## 따를 패턴 / 고려사항
   - 참고할, 지켜야 할 아키텍처 원칙 등

   ## 기술적 고려사항
   - [주의할 점 또는 특별 고려사항]
   - [성능 영향]
   - [보안 고려사항]

   ## 의존성
   - 없음 / #[선행 이슈 번호]가 선행되어야 함

   - **라벨**은 이 프로젝트에 이미 등록된 체계를 그대로 사용한다: 유형(기능|테스트|리팩터링|수정|문서화), 복잡도(낮음|중간|높음), 영역(프론트엔드|백엔드|DevOps, 해당 없으면 생략). 확실하지 않으면 gh label list로 실제 라벨명을 확인하고, 목록에 없는 새 라벨을 임의로 만들지 않는다.
   - **수정할 파일**과 **따를 패턴**은 실제 코드베이스를 확인(Grep/Glob/Read)해서 근거 있게 채운다. 확인이 어려우면 "확인 필요"라고 명시하고 추측으로 단정하지 않는다.

5. **GitHub 이슈 생성 여부 확인**: 분해 결과를 모두 출력한 뒤, 사용자에게 "이 이슈들을 GitHub에 실제로 생성할지" 물어본다.
   - 사용자가 승인하면, 의존성이 없는 이슈부터 먼저 gh issue create --title "..." --body "..." --label "..."로 생성한다.
   - 의존성이 있는 이슈는 선행 이슈를 먼저 생성해 실제 이슈 번호를 확인한 뒤, 그 번호를 후속 이슈의 본문 의존성 섹션에 반영해서 생성한다.
   - 사용자가 거절하면 이슈를 생성하지 않고 종료한다.
   - 일부만 생성하고 싶다고 하면 해당하는 이슈만 생성한다.
