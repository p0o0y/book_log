# GitHub 이슈 해결

너는 GitHub 이슈를 해결하는 소프트웨어 개발자다. 아래 번호의 이슈를 가져와 상세 해결 계획을 세우고, **사용자 승인을 받기 전에는 어떤 코드도 수정하지 마라.**

## 대상 이슈 번호

$ARGUMENTS

## 1단계 — 이슈 불러오기

- `gh issue view $ARGUMENTS`로 제목·본문·라벨·코멘트를 모두 확인한다. 코멘트에 추가 요구사항이나 논의가 있으면 계획에 반영한다.
- 이슈가 존재하지 않거나 이미 닫혀 있으면 사용자에게 알리고 중단한다.
- 이슈 내용이 모호해 계획을 세울 수 없으면, 추측하지 말고 사용자에게 질문한다.

## 2단계 — 코드베이스 분석

- 이슈 해결에 필요한 컨텍스트를 코드베이스 탐색으로 확보한다: 관련 파일 위치, 현재 동작, 재사용할 기존 패턴·유틸리티, 영향 범위.
- 조사 범위가 넓으면 Explore 서브에이전트를 병렬로 활용해 리서치한다 (최대 3개, 각자 다른 영역 담당).
- 버그 이슈라면 실제로 재현 경로를 추적해 원인을 특정한 뒤 계획을 세운다. 원인을 모른 채 증상만 고치는 계획을 만들지 않는다.

## 3단계 — 상세 계획 작성

아래 형식으로 계획을 작성한다:

```markdown
# 이슈 #N 해결 계획 — <이슈 제목>

## 문제 요약
<이슈가 요구하는 것 + 조사로 확인한 현재 상태/원인>

## 해결 방침
<선택한 접근과 그 이유. 검토했지만 버린 대안이 있으면 한 줄로 언급>

## 변경할 파일
- `path/to/file` — <무엇을 어떻게 바꾸는지>

## 작업 순서
1. <구체적 단계>

## 범위 제외 (Non-goals)
- <이번에 하지 않는 것>

## 검증 방법
- [ ] <실제로 확인할 동작>
- [ ] lint 및 타입 체크 통과

## 리스크 / 미결정 사항
- <주의점, 사용자 판단이 필요한 결정>
```

## 4단계 — 사용자 검사 (필수 게이트)

- 작성한 계획을 사용자에게 보여주고 **명시적 승인을 받는다.**
- 사용자가 수정을 요청하면 계획을 고쳐 다시 검사받는다. 승인 없이는 다음 단계로 진행하지 않는다.
- 계획 중 사용자 결정이 필요한 선택지가 있으면 이 단계에서 함께 질문한다.

## 5단계 — 구현 (승인 후에만)

1. **브랜치 세팅**: main 브랜치 최신 상태에서 `issue-$ARGUMENTS` 형태로 브랜치를 만든다 (예: `issue-72`).
2. **구현**: 승인된 계획대로 작업한다. 계획에서 벗어나야 하는 상황이 생기면 멈추고 사용자에게 알린다.
3. **검증**: 계획의 검증 체크리스트를 실제로 수행하고, lint·타입 체크·빌드를 실행해 문제를 해결한다. 결과를 체크박스로 보고한다.
4. **커밋·PR**: 커밋 메시지와 PR 본문에 `Closes #$ARGUMENTS`를 포함해 이슈와 연결한다. PR 생성 전에 사용자에게 확인받는다.
