# 작업 세분화

다음 문제를 독립적으로 실행 가능한 작은 작업 단위로 분해하라.

## 해결할 문제

$ARGUMENTS

## 진행 절차

1. **목표 정의**: 위 문제의 완료 상태(Definition of Done)를 한두 문장으로 먼저 정의한다. 문제가 모호하면 분해 전에 사용자에게 질문한다.
2. **컨텍스트 조사**: 추측으로 나누지 말 것. 관련 코드·문서·기존 패턴을 먼저 탐색해 현재 상태와 재사용 가능한 것을 파악한 뒤 분해한다.
3. **분해**: 아래 기준을 만족하도록 작업을 나눈다.
4. **자기 점검**: 각 단위가 기준을 벗어나면 재분해(너무 큼)하거나 병합(너무 작음)한 뒤 최종 출력한다.

## 분해 기준

- 각 단위는 **그 자체로 실행·검증·머지 가능**해야 한다 (절반만 동작하는 상태로 끝나지 않을 것)
- 한 단위 = **한 번의 작업 세션(PR 하나) 규모**
- 단위 간 **의존 관계를 명시**하고, 의존이 없는 단위는 병렬 가능으로 표시
- 서로 다른 단위가 **같은 파일을 크게 수정하지 않도록** 경계를 나눈다
- 분해에 영향을 주는 **미결정 사항은 작업이 아니라 "질문"으로 분리**한다

## 출력 형식

각 작업 단위를 아래 템플릿으로 작성한다. 독립적인 에이전트가 다른 맥락 없이 이 문서만 보고 작업할 수 있도록 충분한 컨텍스트(관련 파일 경로, 기존 패턴, 주의사항)를 담을 것.

```markdown
# Task N — <제목>

> 선행 조건: Task M 완료 (없으면 "없음 — 병렬 가능")

## 오버뷰
<이 단위에서 해결하는 것, 배경 컨텍스트, 구현 방침, 관련 파일 경로>

## 범위 제외 (Non-goals)
- <이 단위에서 하지 않는 것>

## 작업 항목
- [ ] <구체적 작업>

## 검증 체크리스트
- [ ] <완료 후 실제로 확인할 동작>
- [ ] lint 및 타입 체크 통과
```

마지막에 **전체 요약 표**(Task 번호 / 제목 / 의존성 / 예상 규모)와 **미결정 질문 목록**을 출력한다.

사용자가 파일로 저장을 요청하면 `docs/plans/` 아래에 Task별 개별 md 파일로 저장한다.
